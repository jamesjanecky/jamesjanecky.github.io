0The Unity mental model in one page

Unity conceptWhat it is, in software terms
Scene (.unity)A serialized object graph loaded at runtime. We have one real scene: Assets/_Project/Scenes/Lanternfall_Greybox.unity.
GameObjectAn entity: a named node in a transform tree, with no behaviour of its own.
ComponentBehaviour or data attached to a GameObject (composition over inheritance). Transform, Collider, Renderer, AudioSource, and our own scripts.
MonoBehaviourA C# class that is a component. Unity calls its lifecycle methods by reflection (Awake, OnEnable, Start, Update, LateUpdate, OnDisable, OnDestroy).
Prefab (.prefab)A serialized GameObject template you instantiate many times, like a class you can new (e.g. Prefabs/Enemies/Drowned.prefab).
ScriptableObject (.asset)A serialized data object that lives as a file, not in a scene. We use these as config files: every tunable number is in one (Data/Config/*.asset, Data/Weapons/*.asset).
[SerializeField] privateA private field Unity saves into the scene/prefab/asset and shows in the Inspector. This is how dependencies are wired (an inject-by-editor DI).
.meta filesEach asset's stable GUID. References between assets are by GUID, so never delete or hand-edit a .meta.
The frame loopSingle-threaded main loop. Every frame: input, then Update on every enabled component, animation, LateUpdate, then rendering. FixedUpdate runs at a fixed physics rate.
Time.deltaTimeSeconds since the last frame. Anything that moves or counts down multiplies by it, so behaviour doesn't depend on frame rate. Time.timeScale = 0 freezes scaled time, which is how a solo pause works.

Two things surprise most engineers:

  1. Almost everything runs on the main thread, once per frame. There is no request/response; there is "what changed this frame". Performance is a per-frame budget: about 16.6 ms at 60 fps for all game code plus rendering.
  2. Garbage collection causes visible hitches. A GC pause of a few milliseconds is a dropped frame. So hot paths (Update, per-shot, per-hit code) must not allocate. See section 13.

1Project architecture

Assemblies (compile units)

AssemblyFolderContents
Game.RuntimeScripts/ (minus Editor)Everything that ships in the game. References Input System, AI Navigation (NavMesh), URP.
Game.EditorScripts/Editor/Editor-only tooling: the map builder, procedural art kit, playtest builder, asset setup. Never in a build.
Game.Tests.EditModeAssets/_Project/Tests/EditMode/NUnit tests (~170 files, ~1,700 test cases), run inside the Editor.

.asmdef files define these. Splitting assemblies means a change only recompiles its own assembly and the ones that depend on it, and it stops runtime code from calling editor APIs (which would fail the build).

Folders by feature, namespaces by feature

Scripts/ has one folder per system: Core, Player, Weapons, Enemies, Waves, Economy, Interaction, Perks, PowerUps, Chest, Anvil, Shards, Relics, Starbow, Shield, Grenades, Lantern, Lure, MainQuest, Keeper, Victory, World, Feel, UI. Namespaces match (Game.Weapons, Game.Enemies, ...).

The core pattern: thin MonoBehaviours, plain C# rules

This is the most important convention in the codebase:

  • Rules (damage math, wave scaling, fire timing, pause logic, spawn choice) live in plain C# classes, often static, with no Unity lifecycle. They take inputs (including the current time) as parameters and return results.
  • MonoBehaviours are thin adapters. They read input and the scene, call the rules, and apply the results to Unity objects.

Why: plain classes are deterministic and testable in milliseconds without starting the game. A few examples:

Rule classWhat it decidesUsed by
Scripts/Waves/RoundMath.csenemy count, health, spawn interval per roundRoundManager
Scripts/Weapons/FireTimer.cshow many shots fire this frame, frame-rate independentHitscanWeapon
Scripts/Core/Hitbox.cs (HitZone)headshot / weak-point multipliersHitscanWeapon, Damageable
Scripts/Economy/PointRules.cspoints for a hit or killPlayerCore
Scripts/Core/PauseService.cswhether the game is paused, by owner setGameManager

PauseService is a good example of ports and adapters: it writes its result through an IPauseSink interface. At runtime the sink sets Time.timeScale and the input gate; in tests it's a fake that records calls.

Cross-system communication: C# events

Systems talk through event Action<...> rather than calling each other directly. For example, RoundManager raises RoundStarted, RoundEnded, EnemyKilled and GameOver, and Zombie raises Killed, Damaged, Despawned and AttackStarted. Audio, VFX, UI, quests and relics subscribe, and the producer doesn't know they exist. This is an in-process observer/pub-sub. The rule is to unsubscribe in OnDisable/OnDestroy, or you leak references and get callbacks on destroyed objects.

One manager, no other singletons

Scripts/Core/GameManager.cs is the only singleton (GameManager.Instance). Other systems are found through serialized references or passed in. Static state is avoided, and where it exists (debug toggles, caches) it is reset in a [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)] method. That matters because the Editor can enter Play mode without reloading the C# domain, so statics would otherwise survive from the last session.

Partial classes split big components

RoundManager is split into RoundManager.cs, .Hounds.cs, .Bellringer.cs, .FightAdds.cs, .QuestSurge.cs, .QuestHold.cs and .Relics.cs. Zombie has .Hound.cs, .Bellringer.cs, .Lure.cs, .Blast.cs and .Debug.cs. The same component, but one file per concern, so feature work touches small files.

2Game flow and lifecycle

Startup order

Unity calls Awake on every object, then Start, in an order you don't control unless you set [DefaultExecutionOrder(n)] (lower runs first). We pin the few that matter:

OrderComponentWhy first
-1000World/RuntimeNavMeshBakerBakes the navigation mesh in Start (not Awake, because modifiers only register in their OnEnable). Nothing may path before it.
-500World/LighthousePowerResets the power state so machines start unpowered.
-300Core/GameManagerReads Esc before UI panels, so one key press doesn't both close a card and open the pause menu.

The game state machine

Core/GameFlow.cs is a small pure state machine: MainMenu, Playing, Paused, GameOver, with CanTransition(from, to) and a Changed event. GameManager owns it, plus the cursor and pause service. The main menu is drawn over the live town: the round loop idles, the player camera is off, and UI/MenuCamera orbits.

Restarting = reloading the scene

Restart, Retry and Quit to menu reload the whole scene (RoundManager.Restart()), which is the simplest way to guarantee a clean slate. Because a reload destroys every object, the one value that must survive, "land in the menu or straight in a run?", sits in a tiny static: Core/SessionLaunch.cs (Request before reload, Consume in GameManager.Awake).

Pausing

Any system that needs a pause (pause menu, level-up cards, path cards, game over) calls GameManager.Pause.RequestPause(owner) and later ReleasePause(owner). The game is paused while any owner holds it, so overlapping modals can't un-pause each other (a reference-counted lock). The policy is FreezeWorld in solo (timeScale 0 + input gate). For co-op it can become Overlay (only that player's input is gated) without changing any caller. Player/InputGate.cs is the matching input lock, with a short "fire block" after unpausing so the click that closed a menu doesn't also fire the gun.

3The player

Player/PlayerCore.cs is the hub. Other systems talk to "the player" through it: Wallet (points), Stats, Health, Weapons, Controller, Perks, Relics, and points multipliers. Per-player state lives on the player, never in statics, because co-op is planned.

  • Movement: Player/FirstPersonController.cs uses Unity's CharacterController (a capsule with collide-and-slide movement, no rigid-body physics) and the new Input System (Assets/InputSystem_Actions.inputactions: named actions like Fire, Aim and Interact, bound to keyboard and gamepad). It includes a wall guard, so a crowd pushing the capsule can't squeeze it through thin walls.
  • Health: Player/PlayerHealth.cs handles damage, regen, the downed state and Second Wind. Enemy melee arrives as TakeDamage(amount, attackerPos) so the HUD can show which direction a hit came from.
  • Interaction: Interaction/PlayerInteractor.cs + Interactable.cs. Doors, wall buys, machines and quest objects are interactables with a prompt and a hold time.

4Combat: from trigger pull to damage

This is the most important pipeline to understand. In order:

  1. Trigger. Weapons/PlayerWeapons.cs routes input to the held weapon. Weapons/HitscanWeapon.cs asks FireTimer how many shots to fire this frame. An 850 RPM gun at 60 fps fires 14.2 shots per second, so the timer carries the fractional remainder between frames instead of rounding to whole frames.
  2. Hitscan. Every gun is hitscan: the bullet is an instant ray, Physics.Raycast from the camera along the aim plus spread, not a flying object. Piercing guns use Physics.RaycastNonAlloc into a preallocated RaycastHit[] buffer (no garbage). The visible tracer is just a visual effect.
  3. Hit zones. The ray hits a collider. If it carries a Core/Hitbox.cs (head or weak point), the multiplier comes from HitZone.Multiplier. Enemy colliders are invisible boxes separate from the visible mesh, so the art can change without changing gameplay.
  4. Damage. The weapon builds a DamageInfo (a readonly struct, passed in so it isn't copied: amount, point, direction, headshot, source, DamageKind, crit, element, ...). It calls IDamageable.TakeDamage(in info) on the target's Core/Damageable.cs.
  5. Shaping. Damageable runs the optional per-target hooks:
    • IDamageShaper: armour, such as the Bellringer's front shell at x0.2;
    • IDamageBonus: e.g. a relic's mark.

    Then it applies the result to Health, flashes the renderers and returns a DamageResult (applied, killed).

  6. Consequences fan out through events. The Zombie.Damaged and Killed events drive:
    • points, via PointRules and the player's wallet;
    • shards and power-up drops;
    • feel: damage numbers, hit stop, sounds, VFX;
    • relic procs and quest progress.

    The weapon also fills a ShotReport (all hits of one shot) for the hit marker and recoil feel.

DamageKind (Bullet, Melee, Explosive, PowerUp, Element, Relic) is how downstream code tells hits apart: element ticks pay no hit points, power-up kills drop nothing, relic hits never proc elements, and so on. Enforcing those rules in one enum keeps them out of a dozen if chains.

Other weapon types plug into the same pipeline: the Starbow (Scripts/Starbow/, hold-to-draw hitscan), grenades and the lure (Scripts/Grenades/, Scripts/Lure/, kinematic sweeps + BlastRules falloff), and the Lantern (Scripts/Lantern/, pooled bolts that chain).

5Enemies and AI

The Drowned: a state machine on a NavMeshAgent

Enemies/Zombie.cs is the enemy brain, a classic finite state machine:

Inactive -> Approaching -> Breaching -> Climbing -> Chasing <-> Attacking -> Dying -> (back to the pool)
                                        (Emerging, Lunging: hound / Tidecrawler variants)

Update switches on State and calls UpdateApproach, UpdateBreach and so on. Each state is a few lines of "check conditions, maybe transition".

Pathfinding: NavMesh

Unity's NavMesh is a precomputed polygon mesh of walkable floor. A NavMeshAgent component does A* on it plus local steering and avoidance; you set a destination and it walks there. Our town is generated, so the NavMesh is baked at load by World/RuntimeNavMeshBaker.cs. Props that must not block it get a NavMeshModifier set to ignore them. Solid props get a "Not Walkable" volume.

Animation without an Animator

Most games use Unity's Animator with authored clips. Ours is procedural: Enemies/DrownedAnimator.cs and Enemies/CreatureMotion.cs compute limb rotations every frame from walk speed, a seeded per-enemy personality, damped springs (head lag, arm lag) and fixed timing envelopes (wind-ups, hit reactions, deaths). It's math-driven, testable, and costs nothing to author. Tests pin the attack timings so animation changes can't change gameplay.

Variants, pooling and look

  • One prefab carries every Drowned variant's rig. EnemyVariant ScriptableObjects (Data/Enemies/Variant_*.asset) pick the rig and tune speed, health and weak points.
  • Object pooling: enemies are never Instantiated or Destroyed during play. RoundManager keeps a pool; GetFromPool reuses an inactive Zombie, Spawn(...) resets it, and dying ends with SetActive(false) and a Despawned event. Creating and destroying objects is slow and makes garbage; pools turn it into a reset.
  • Visual LOD: Enemies/CreatureLook.cs swaps mesh detail by distance and graphics preset (plain rules in CreatureDetail.cs). CreatureRim.cs adds a silhouette rim light through a per-renderer shader value.

Bosses and specials

  • The Keeper (Scripts/Keeper/) follows the same split: plain classes KeeperBrain, KeeperAttackScheduler, CarapaceRules and KeeperGeometry decide everything. KeeperBoss and KeeperRig apply it to the scene.
  • Hounds and the Bellringer are Zombie partials with their own schedules in Scripts/Waves/.

6Rounds and spawning

Waves/RoundManager.cs runs the core loop: BeginRun → StartRound(n) → spawn the round's enemies over time → all dead → intermission → next round. Inputs:

  • RoundConfig (ScriptableObject) holds the curve parameters. RoundMath turns them into enemy count (a quadratic in the round number, capped), health (linear, then exponential), and spawn interval (shrinking to a floor).
  • Waves/SpawnRules.cs picks a spawn window: the nearest usable windows to the player, a minimum distance, a preference for the player's own area, and a vertical weight for the tunnels.
  • Waves/VariantMix.cs decides which Drowned variant each spawn is, by round.

Special rounds and events are partials and schedules: hound rounds every 5th round (HoundSchedule), the Bellringer (BellringerSchedule), quest surges, boss-fight adds that never touch round counts, and relic offers every 3rd round.

7Economy and progression

  • Points: Economy/PointsWallet.cs (per player) + PointRules.cs + EconomyConfig. Doors, wall buys, perks, the chest and the Anvil spend from it.
  • Perks (Scripts/Perks/): machines grant passive buffs, up to 4, lost on going down.
  • Weapons upgrade (Scripts/Anvil/): forging adds a runtime WeaponUpgrade to a HitscanWeapon, while the base WeaponData asset stays the gun's identity. Elements (Burn, Chill, Chain, Ricochet) run in ElementStatusSystem.
  • Run upgrades (Scripts/Shards/): XP shards → level-up → pick 1 of 3 cards → WeaponModifiers.SetRun.
  • Relics (Scripts/Relics/): passive weapons with levels and twists, attached at runtime by RelicSystems.Attach.
  • Random rewards (Scripts/Chest/): ChestRules.RollPrize pre-rolls special prizes, then the gun. Every random draw goes through an injected rng01 function, so tests can make the outcomes deterministic.

8Quests and the main quest

The Starbow paths use a small data-driven step machine: Starbow/Quest/QuestStepMachine.cs + QuestStepDef (types such as ShootTargets, KillNear, Carry, Retrieve and HoldZone, each Locked → Active → Done). A quest is data, so a new quest is mostly a list of step definitions plus markers in the scene. The main quest (Scripts/MainQuest/) reuses step ideas with its own director: the lens, logs, Midnight bell and boss gate.

9Game feel: audio, VFX, camera

"Feel" is the layer that makes actions satisfying. It all lives in Scripts/Feel/ and reacts to events.

  • Audio: only Feel/SfxPlayer.cs (and the ambience/music directors) may play sounds; a test greps for violations. SfxPlayer owns fixed pools of AudioSources (VoicePool), with priority stealing when all voices are busy and distance low-pass filtering. AudioBusRules implements buses and ducking (e.g. telegraph sounds lower everything else) in code, with no AudioMixer.
  • Music: MusicDirector schedules stems with AudioSource.PlayScheduled, which is sample-accurate, so loops and layer swaps land exactly on the bar.
  • VFX: one pooled Feel/Vfx.cs service drives 3 particle systems and a ribbon mesh for every effect in the game. Effects are "emit N particles here", not GameObjects. VfxBudget thins effects by preset and crowd size.
  • Camera and timing:
    • TraumaShake / CameraShaker: shake that the aim ignores.
    • HitStop: a few-millisecond freeze on big hits.
    • Spring: damped springs for view kick.
    • Player/ViewSway: weapon bob and sway.

10Rendering

  • URP (Universal Render Pipeline) is Unity's configurable forward renderer. Its settings are assets in Assets/Settings/ (PC_RPAsset, the renderers PC_Renderer and PC_Renderer_LiteAO).
  • Custom shaders (Art/Shaders/, HLSL in ShaderLab): LanternfallFlat (environment), LanternfallFlatCreature (enemies, guns), LanternfallFxAdditive (VFX), LanternfallInkOutline (gun outlines) and LanternfallSky.
  • Flat-shaded low poly via vertex colours: most of the world uses one material, M_Kit_Flat. Colour lives in the mesh's vertex colours and glow in vertex alpha, so thousands of pieces share one material. That keeps GPU state changes ("SetPass calls") low, and those, more than triangles, are what cost on integrated GPUs.
  • Draw calls and batching: every visible mesh x material is a draw call. Batching combines them:
    • The kit combines decoration per area and 16 m cell into a few meshes.
    • Shaders stay SRP-batcher compatible: per-material data sits in one constant buffer, and per-object variation goes through MaterialPropertyBlock or Renderer.SetShaderUserValue.
  • One writer for global state: World/SkyDirector.cs is the only runtime code that writes RenderSettings (fog, ambient), the sky and the post-processing volume. It blends looks from state weights (round, low tide, Midnight, arena, dawn) through plain SkyBlend and PostBlend classes. One owner for shared mutable state avoids fights between systems.
  • Graphics presets: Data/UI/GraphicsPresetConfig plus UI/SettingsApplier set shadows, culling, detail tiers and the renderer per preset.
    • Detail tiers are hidden on Low with Renderer.forceRenderingOff (World/KitTiers.cs).
    • Clutter is culled per layer with Camera.layerCullDistances.

11UI

Unity's UI Toolkit is like a retained-mode DOM: layout files Art/UI/*.uxml, stylesheets *.uss, and C# that binds to elements. Patterns used:

  • Model/view split: UI/Hud/HudModel is pure (what to show) and HudView binds it to elements, so the HUD logic is testable.
  • UI/Hud/NotificationQueue.cs (ToastQueue, BannerQueue) handles toasts and banners with priority and merging.
  • UI never pauses the game directly; it goes through PauseService.

12Settings and persistence

  • Core/Settings/GameSettings.cs is a plain class serialized to JSON, stored through an ISettingsStore: PlayerPrefs at runtime, in-memory in tests. UI/SettingsApplier.cs applies changes live.
  • Victory records (Victory/VictoryRecordStore) use versioned JSON, so old saves can be migrated.
  • There is no save-game mid-run (by design: a run is a session).

13Performance practices (why the code looks the way it does)

RuleWhyExample
No allocation in Update or per hitGC pauses drop framespreallocated RaycastHit[], readonly struct DamageInfo passed in

Write only on changeredundant GPU/state writes costKitTiers, CreatureRim, SkyDirector compare before writing
Measure, don't guessintuition is often wrongEditor/Kit/ArtSweep (draws/SetPass/tris per view and preset), Settings > Video > Show FPS (UI/Perf/PerfOverlay, FrameTimingManager)

A real example: the Medium preset was over its draw-call budget. Measuring showed the cause wasn't the art but the SSAO effect's depth-normals prepass, which drew every object twice. Switching to a renderer whose AO reads the existing depth buffer roughly halved draw calls on every preset (Core/Settings/PresetRendering.cs, Docs/Design/ArtPass2.md section 13).

14The content pipeline: the map is generated by code

The scene isn't hand-built in the editor. Scripts/Editor/GreyboxMapBuilder.cs (+ ~35 partial files, about 8,500 lines) runs from Game > Build Greybox Map and creates the whole town in code:

  • walls, doors, windows, markers, machines and quest objects;
  • wiring the serialized references between them;
  • saving the scene and prefabs.

Then the art kit (Scripts/Editor/Kit/) runs last. It is a set of seeded procedural mesh generators (facades, roofs, props, creatures, weapons). It restyles and decorates the greybox, combines meshes, and validates the result:

  • every decoration piece is checked against keep-out zones around gameplay objects;
  • colliders are diffed before and after;
  • the NavMesh is compared before and after;
  • every gameplay marker must have a keep-out.

Why build a level this way:

  • It's reviewable and diffable code instead of opaque scene edits.
  • It's reproducible: same seed, same town.
  • Art can't silently break gameplay, because the validator fails the build.

Audio is generated too: Tools/sfx_gen.py and Tools/music_gen.py synthesise every sound and the music stems. They are checked against manifests, and size budgets apply.

15Testing, tooling and debugging

  • EditMode tests (Assets/_Project/Tests/EditMode/) use NUnit through the Unity Test Framework, run inside the Editor. They mostly test the plain rule classes, plus asset and prefab checks (e.g. "no Danger Red on enemy colours", "hit-zone colliders unchanged", "the enemy shader has 4 passes").
  • Unity CLI (~/.unity/bin/unity): recompile, run tests, invoke editor menus, evaluate C# in the running game, and capture screenshots from the terminal. This is how the AI agents drive the Editor (see CLAUDE.md).
  • Stop hook (.claude/hooks/unity-check.sh): after any C# change, recompiles and runs the tests before the agent may finish.
  • Debug commands: every system has a *Debug static class compiled only in editor and dev builds (#if UNITY_EDITOR || DEBUG), e.g. Game.Endgame.KeeperDebug.SetPhase(2), callable through script eval. There is also an F1 dev panel in dev builds.
  • Builds: Scripts/Editor/PlaytestBuilder.cs makes the Windows x64 playtest zip with HOW_TO_PLAY.txt.

16Designed for co-op later

The game is solo, but the code avoids decisions that would block co-op:

  • per-player state on the player, not in statics;
  • enemies pick a target rather than "the player";
  • pause through a policy that can become an overlay;
  • rules are deterministic and seeded, which matters if a server or host must agree with clients;
  • players are looked up through one place, not FindAnyObjectByType scattered around.

17A suggested learning path

  1. Read the damage pipeline end to end: HitscanWeapon.Fire → Damageable.TakeDamage → Zombie events → PointRules. Then read its tests (search Tests/EditMode for HitZone, PointRules, FireTimer).
  2. Read Zombie.cs's state machine with a Drowned spawned in Play mode. Use Game.Enemies.DrownedDebug.Spawn("Netter") and watch the State field in the Inspector.
  3. Change a number, not code: open Data/Config/RoundConfig (or a WeaponData asset) in the Inspector, change a value, and play. This is the designer's loop that ScriptableObjects enable.
  4. Use the Profiler (Window > Analysis > Profiler) during a crowd fight. Find Zombie.Update and SfxPlayer, and check the GC Alloc column stays at 0.
  5. Use the Frame Debugger (Window > Analysis > Frame Debugger) to watch one frame draw call by call. It is the best way to understand batching and SetPass.
  6. Small exercises:
    • Add a new DamageKind behaviour with a test.
    • Add a new run-upgrade card.
    • Write a new quest step type for QuestStepMachine.

Glossary

TermMeaning
HitscanA shot resolved instantly by a raycast, with no projectile object.
NavMesh / NavMeshAgentPrecomputed walkable surface / the component that paths and steers on it.
Draw callOne "draw this mesh with this material" command to the GPU.
SetPass callA GPU state change (new shader or material setup). Often the real bottleneck on weak GPUs.
SRP BatcherURP's fast path that keeps per-material data on the GPU, so many objects draw cheaply.
MaterialPropertyBlockPer-renderer shader overrides without creating new materials.
LODLevel of detail: cheaper visuals at distance.

Hit stopA tiny freeze on impact that makes hits feel heavy.
